# Review gate

Before opening or merging a PR/MR, merging into the base branch, pushing to it or pushing to the branch of a PR you opened, the guard asks the user unless the reviewer's last verdict is `Yes` for the commit being landed and covers the whole branch. The guard records the verdict and the report from a `subagent` result that carries the reviewer's `Reviewed BASE:`, `Reviewed HEAD:` and `Ready to merge:` lines; you never write them yourself. Run the reviewer in the foreground, so its report comes back as that result.

- **A verdict covers exactly the commit the reviewer reviewed** (its `Reviewed HEAD`). Any change after it needs a new review: a new commit, an amend, a rebase onto a newer base, a docs edit, deleting the task file. A branch that changes only documentation is reviewed the same way. So review last: after docs, the task-file removal and any rebase. Commits already on the remote base land nothing new and need no review.
- **The range must reach the remote base.** A review counts when its `Reviewed BASE` is on the remote base branch (the push remote's, else `origin`'s, else any remote's; the local base branch only when no remote tracks it), or is itself a commit whose review counts by the same rule. A repeat round can review only the new commits, and the chain still covers the whole branch, up to 20 rounds. A round must start at the newest reviewed commit below it: skipping a reviewed commit would skip its findings. A rewritten history breaks the chain: review from the merge-base again. An empty range (`BASE` = `HEAD`) covers nothing, and so do records written before 0.14.0, which have no range: after updating, review each branch once more. A chain the guard can't check within its budget of git calls doesn't count either. A reviewer run that failed records no range, so a repeat round can't chain through that commit: review it again, or review from the merge-base.
- **Earlier findings come from the store.** In a repeat round the reviewer first runs `node <kit root>/scripts/review-log.ts <BASE>`, which prints that round's reports, and re-checks every finding in them. You don't pass the findings on yourself. Records are kept per repository (its git common directory), so the script finds them from any folder or worktree.
- **A PR you opened is a landing target.** When a `gh pr create` or `glab mr create` call succeeds, its branch (`--head`/`-s`, else the branch where the command started) is registered, and pushing to it needs the same review. The branch is forgotten once the PR's head (`origin/<branch>`) is on the base, or after 30 days. A PR opened outside this agent (in the browser, by another tool) is not seen.
- Land in a command of its own: a landing chained after anything but read-only steps (`cd`, `git status`/`diff`/`log`/`add`/`fetch`, `cat`, `grep`…) and the project's verification commands asks (blocked without a UI), because the guard can't see the commit it would land. A `cd` the guard can't follow (a variable, `$(…)`, a nested subshell, a missing folder; a `cd` inside one `( … )` is followed and ends with it) or `-R` to another repository asks too. `gh pr merge <number>` asks, because the PR's head isn't known locally; name the branch, or merge from it (the remote branch is checked as well).
- Only runs of the `reviewer` agent count. A run that fails, times out, gives no verdict or lacks one of the three lines (pi doesn't send it back) counts as `Inconclusive` for the commit it reviewed, within that round. A review of a later commit is unaffected.
- A review counts only for verified code: one that ran while edits were unverified (the verify gate wasn't green) is recorded as `Inconclusive`. Run the checks first, then review.
- `With fixes`, `No` and `Inconclusive` don't pass: fix, then re-review the new range.
- Only the user can waive the gate: by confirming, or with `"reviewGate": false` in `.pi/guard.json` (trusted projects only; the guard asks before that file is edited). A self-review in a separate pass does not satisfy the gate, so without a `subagent` tool the user decides at the prompt.
- The reviewer's read-only rule is an instruction here: pi doesn't tell the guard which agent runs a call, so its shell isn't restricted.
- If a guard check throws, pi blocks the call with the error ("Extension failed, blocking execution").
