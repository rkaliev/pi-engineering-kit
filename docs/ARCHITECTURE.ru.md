# pi-engineering-kit: как это устроено

English version: [ARCHITECTURE.md](ARCHITECTURE.md)

pi-engineering-kit — это пакет для кодинг-агента [pi](https://pi.dev), который делает из него дисциплинированного инженера. Пакет подходит для любого проекта и подстраивается под него по трём независимым осям:
- **где работает код:** web, мобильные приложения (Android, iOS), десктоп (Windows, Linux);
- **что он делает:** от развлекательных приложений до кассовых систем и платежей; там, где ошибка стоит дорого (деньги, фискализация, безопасность), есть отдельные скиллы;
- **в каком состоянии код:** новый проект или существующий, в том числе написанный задолго до агентной разработки.

Поверх этих осей работает один и тот же процесс: дизайн → план → TDD → проверка → ревью → git.

Здесь описано, как устроен пакет и почему он устроен именно так. Как установить и попробовать — в [GETTING-STARTED.ru.md](GETTING-STARTED.ru.md).

---

## 1. Идея в трёх предложениях

1. **Процесс масштабируется по размеру задачи.** Мелкая правка проходит короткий путь, архитектурная — полный путь от файла задачи до ревью. При сомнении выбирается более тяжёлый путь. Минимум задаёт риск: CI и release-пайплайны, права, auth, секреты, деньги, схема БД и конфигурация деплоя никогда не идут коротким путём, даже если правка маленькая.
2. **Модель сама не решает, что работа готова.** Это решают проверки проекта. Гейт в расширении возвращает агента к работе, если после правок не было зелёного прогона.
3. **Необратимое и внешнее проходит через человека.** Расширение guard блокирует опасные команды и спрашивает подтверждение на деплой, миграции, публикацию, merge и любой push, кроме обычного push своей рабочей ветки.

## 2. Архитектура

```
┌─────────────────────────────── проект ────────────────────────────────┐
│ AGENTS.md (команды, правила, границы, DoD)   .pi/verify.json   .pi/guard.json │
└──────────────────────────────────┬────────────────────────────────────┘
                                   │ читают
┌──────────────── pi-engineering-kit (этот пакет) ────────────────────────┐
│ extensions/bootstrap.ts  → в каждый запрос: скилл using-skills          │
│ extensions/guard.ts      → tool_call: block / confirm / allow           │
│ extensions/verify.ts     → /verify, run_verification, гейт на agent_end │
│ extensions/models.ts     → модель и thinking по команде, /mode          │
│ extensions/init.ts       → /kit-init: .pi/ проекта одной командой       │
│ skills/   28 скиллов (процесс, старт, платформы, домены), по описанию│
│ prompts/  9 точек входа: /brainstorm /plan /implement /review …         │
│ templates/ AGENTS.md, task.md, verify.json, ts-monorepo/, …             │
│ scripts/  test-hygiene.ts (/kit-init --test-hygiene), scaffold-template │
└─────────────────────────────────────────────────────────────────────────┘
```

**Рабочий цикл:**

```
идея ──/brainstorm──▶ классификация: Spike | Bounded | Architectural
  Spike ─────────▶ проба → рекомендация (код одноразовый)
  Bounded ───────▶ дизайн в чате → «да» → /implement (TDD) → verify → отчёт
  Architectural ─▶ файл задачи → «да» → /plan → «да» → /implement (executing-plans)
                    → requesting-code-review → /finish (merge / PR / keep / discard)
баг ──/debug──▶ systematic-debugging: корень → падающий тест → один фикс → verify
чужой репо ──/onboard──▶ карта → доказанные команды → AGENTS.md + .pi/verify.json
```

**Кто за что отвечает:**
- **Промпты** — тонкие точки входа.
- **Скиллы** содержат всю методику.
- **Расширения** механически обеспечивают то, что нельзя доверить одному тексту.

Благодаря такому разделению пакет не дублирует сам себя: правила готовности живут в одном месте, а не повторяются в каждом промпте.

## 3. Скиллы

### Ядро процесса

| Скилл | Что делает | Почему так |
|---|---|---|
| `using-skills` | Правило «сначала проверь скиллы», приоритеты, три пути (Spike / Bounded / Architectural), таблица «с чего начать», блок «Always true», red flags | Внедряется в каждый запрос, поэтому на нём держатся общие правила: доказательства прежде утверждений, скоуп, тесты, вопросы на развилках, секреты |
| `brainstorming` | Дизайн до кода: классификация работы, по одному вопросу за раз, 2–3 подхода, описание в файле задачи, self-review | Доменные вопросы (деньги, POS, ОС) задаются заранее, потому что потом менять дорого. Несколько независимых подсистем становятся отдельными задачами: одна сейчас, остальные по строке в Follow-ups. Режется только по настоящим швам: каждая задача даёт ценность или шаг раскатки и зелёная сама по себе; цельное изменение не режется ради размера |
| `writing-plans` | План в разделе `## Plan` файла задачи как набор решений, которые исполнитель не примет сам: файлы, сигнатуры, Interfaces, Review focus | План длиннее кода означает, что код уже написан в плане. Исполнение — inline или субагент на задачу |
| `executing-plans` | Исполнение плана с записью в разделе `## Progress` файла задачи, «rulings, not stalls», контракт завершения задачи, режим «субагент на задачу» | Progress — обычный markdown: переживает компакцию и не требует скриптов. `worker`, запущенный на задачу, отчитывается как implementer: изменённые файлы, каждый новый тест и что его видели красным, прогнанные команды с результатами; исправления уходят тому же worker, чтобы он сохранил контекст. На финише то, что остаётся надолго, переносится в `docs/`, Follow-ups показываются пользователю, а файл задачи удаляется одним коммитом |
| `test-driven-development` | Iron Law, RED→GREEN→REFACTOR; `references/test-standard.md` — единственный источник правил тестов, `references/bdd.md` — опциональный слой BDD | «Тест, который не был красным, ничего не доказывает» и «не ослабляй тесты ради зелени». Для legacy сначала характеризационные тесты. Остальные скиллы ссылаются на стандарт, а не пересказывают его |
| `systematic-debugging` | 4 фазы, трассировка корня, «3 неудачных фикса — вопрос к архитектуре» | Границы систем с примерами для POS и мобильных, правило о flaky-тестах |
| `verification-before-completion` | Гейт IDENTIFY→RUN→READ→VERIFY→CLAIM и формат честного отчёта | Раздельно local / commit / push / CI / deploy / live. Pipe в `tail` прячет код выхода |
| `requesting-code-review` | Ревью в свежем контексте по диапазону SHA, шаблон промпта ревьюера, чеклист | **Подтверждено / Предположения / Вопросы**, в каждой находке триггер, последствие и доказательство. Падение сверяется с базовой ревизией. Собственные правила проекта (AGENTS.md, записи решений, которые diff затрагивает или на которые ссылается) — тоже требования. AI-ревью не заменяет одобрение человека |
| `receiving-code-review` | Проверять перед тем, как внедрять; YAGNI через grep | Отклонение замечания — только с конкретным обоснованием |
| `git-workflow` | Изоляция, baseline, коммиты, 4 варианта завершения ветки | Никогда `--no-verify`, force только `--force-with-lease`, discard только по явному вводу. Описание PR ссылается на файл задачи на последнем коммите, где он ещё был |
| `dispatching-parallel-agents` | Группировка по независимым доменам, самодостаточные промпты | Писатели с непересекающимися файлами, без сабагентов — последовательно |
| `writing-documentation` | Где что лежит (README, docs/, записи решений, CHANGELOG, манифест агента, API-справка, комментарии), правила текста и комментариев, что устаревает при изменении кода | Документация — часть изменения: в том же коммите и о текущем состоянии. Перед «docs updated» команды прогнаны, ссылки проверены. Если в проекте свой формат, используется он. Держится на четырёх слоях: правило в этом скилле; блок «Post-implementation» в каждом плане и шаг обновления docs в `/implement` и `executing-plans`; устаревшие docs на ревью — Important; механические проверки (`references/checks.md`) предлагаются в verify и CI проекта |
| `ci-quality-gates` | Проверки в CI проекта | CI запускает минимум всё из verify.json; один обязательный job `gate`; слои по стеку добавляются только с «да»: гигиена тестов (скрипт `test-hygiene` кита и родные линтеры стека), e2e без ретраев со сверкой числа прогнанных тестов по JUnit, sandbox провайдеров отдельным job, секреты и аудит зависимостей, миграции и дрейф, контракты, покрытие как пол по расписанию; job `working-docs`, чтобы файлы задач не попадали в базовую ветку ни от какого автора; защита ветки — только с «да» |
| `updating-dependencies` | Обновление, добавление и удаление зависимостей, SDK и тулчейнов | По одной за раз; changelog прочитан, ломающие изменения выписаны; мажорная версия или новая зависимость — только с «да»; сначала уязвимости; lockfile меняет только пакетный менеджер; полный прогон проверок |
| `writing-skills` | Как писать и тестировать скиллы | Description — только триггеры. Скилл проверяется сценарием без него (RED). Субагенты (pi-subagents): `references/agents.md` |

### Старт: новый или существующий код

| Скилл | Зачем |
|---|---|
| `choosing-a-stack` | Стек выбирается по надёжности для домена. Таблица дефолтов по платформам. **Выбор стека — всегда развилка для пользователя.** Версии сверяются по официальным источникам, а не по памяти |
| `onboarding-existing-codebase` | CI — это правда, команды доказываются прогоном. На выходе AGENTS.md по шаблону с заполненным разделом Docs и `.pi/verify.json` |
| `changing-legacy-code` | Characterization tests, seams, sprout/wrap, strangler fig. Удаляй только свои сироты: странная ветка может быть требованием |

**Профиль TypeScript full-stack.** `choosing-a-stack/references/ts-fullstack-profile.md` — один из кандидатов для нового TypeScript-продукта или SaaS с одной командой и Postgres, но не дефолт. По каждой роли там выбор, причина, когда не брать и альтернатива, а версий нет. Если ты выбрал профиль, `node <kit>/scripts/scaffold-template.ts <абсолютный путь> --postgres <major>` (`<kit>` — папка, куда установлен пакет кита, или его клон) копирует `templates/ts-monorepo/` (pnpm workspaces, Turbo, веб-приложение на Vite, API на Express, Prisma с Kysely, CI). В шаблоне нет версий: скрипт ставит каждый пакет в старшем стабильном релизе не моложе суток, но не выше мажора стабильного тега `latest`, с точной фиксацией; `@types/node` ставится по мажору Node, а пакеты воркспейса — как `workspace:*`. Мажор Postgres не угадывается: передай `--postgres <major>` или `--postgres=<major>` (актуальный поддерживаемый мажор смотри на postgresql.org; без целого положительного числа и с неизвестными опциями скрипт откажется). Он записывается в `.postgres-version`, единый источник, как `.nvmrc`, а `pnpm db:up` и `pnpm db:down` запускают `node scripts/db.mjs up|down` (без shell, поэтому работает и на Windows), чтобы запускать и останавливать по нему локальную базу; healthcheck базы ждёт TCP. Четыре практики этого стека лежат в скиллах без привязки к стеку: CI монорепы в ci-quality-gates (только затронутое, при сбое — всё, один gate), одно хранилище, пока нет замера, в backend-services (существующая база несёт очередь, кеш и блокировки, пока замер не покажет, что нужен отдельный сервис), проверяемая граница клиент/сервер в web-frontend и дисциплина зависимостей в updating-dependencies (у каждого override и патча есть причина и условие снятия).

### Платформы

| Скилл | Зачем |
|---|---|
| `web-frontend` | Семантика и минимум a11y, состояния loading / empty / error / success, гонки и устаревшие ответы, производительность, безопасность, пункты для ревью. В `references/`: где живёт состояние и optimistic-обновления; дизайн-система, дизайн-контекст и тексты деструктивных действий |
| `backend-services` | Конфиг в одном модуле с проверкой при старте, один артефакт на все окружения, процессы без состояния, readiness и liveness, graceful shutdown по SIGTERM, dev ≈ prod, разовые задачи из релиза, API-контракт как источник правды (12-factor без дублирования observability и database-changes). В `references/` лежат правила фича-флагов (OpenFeature в коде, типизированный реестр с безопасными значениями по умолчанию, владельцем и сроком удаления, вычисление не бросает ошибок и откатывается к безопасным значениям, детерминированное распределение, вычисление на сервере, эксперименты по событиям показа) и дополнения к API (внутренний RPC — контракт для открытых вкладок, машиночитаемые коды ошибок, проверка доступа к ресурсу после валидации входа). |
| `mobile-development` | Жизненный цикл, разрешения, безопасность, лестница проверки (unit → release-сборка → эмулятор → устройство). Android и iOS — в `references/` |
| `desktop-development` | UI-поток, пути по платформе, IPC, подпись, автообновление, установка в чистую VM. Windows и Linux — в `references/` |
| `ui-motion` | Анимации и жесты на всех платформах. Сначала гейт: как часто элемент видят и зачем движение; у частых и клавиатурных действий его нет. Затем easing по типу движения, бюджеты до 300 мс, прерываемость, дешёвые свойства, reduced motion как «мягче, а не ноль», физика жестов. Значения и API платформ — в `references/` |

### Домены с высокой ценой ошибки

| Скилл | Зачем |
|---|---|
| `payments-and-money` | Minor units или decimal, ISO 4217, идемпотентность, state machine, таймаут означает «неизвестно», webhooks, outbox, double-entry, сверка, PCI DSS scope |
| `pos-systems` | Offline-first, очередь синхронизации, неизменяемые чеки, фискализация (54-ФЗ; для других стран — «спроси юрисдикцию»), смены X/Z, периферия за интерфейсами |

| `database-changes` | Миграции через expand/contract (работают со старым и новым кодом), обратимость, блокировки, бэкфилл отдельной задачей, порядок деплоя и проверка дрейфа, транзакции и outbox, защитные меры для запросов, жизненный цикл данных, миграции БД на устройствах |
| `security-review` | STRIDE по потокам данных, чеклист (injection, authN/Z, секреты, крипто, supply chain, prompt injection), инструменты, формат находок |

---

**Файл задачи** пишется по шаблону `templates/task.md`, один на каждую единицу работы, и заменяет задачу в трекере:
- Status / Base / Links, исходный запрос дословно, затем Intent / Context / Success criteria / Scope / Decisions / Design / Rollout / Risks and open questions / Follow-ups, затем Plan и Progress;
- у каждого раздела точный заголовок и один вопрос, пустой раздел помечается «None»;
- статус `draft → design approved (дата) → plan approved (дата) → in progress`: brainstorming пишет описание, и ты его одобряешь; writing-plans заполняет `## Plan`, и ты одобряешь его. Статуса «готово» нет: законченный файл задачи удаляется (раздел 5).

До вопросов агент собирает **карту контекста** (`brainstorming/references/context-map.md`) и пишет намерение, допущения и открытые вопросы. Тикеты, старые файлы задач и docs — это гипотезы: каждое утверждение, на которое агент опирается, сверяется с кодом и его тестами. У плана есть `Base:` с SHA коммита, при исполнении проверяется, не ушёл ли код. У PR есть формат описания, и одна тема на PR.

## 4. Расширения

| Расширение | Как устроено | Почему так |
|---|---|---|
| `bootstrap.ts` | На событии `context` вставляет `using-skills` как **user**-сообщение после compactionSummary, с дедупликацией по маркеру | Без bootstrap скиллы инертны: модель видит только их описания. Изменения в `context` не сохраняются в истории, поэтому правила внедряются в **каждый** запрос. Сообщение стоит на стабильной позиции с тем же timestamp и попадает в prompt cache |
| `guard.ts` | Токенизатор с учётом кавычек и цепочек (`&&`, `\|`, `;`). Три решения: block, confirm или allow. Проектный `.pi/guard.json`. Правка CI и release-пайплайнов (`.github/workflows/`, `.gitlab-ci.yml`, `Jenkinsfile` и подобных) требует подтверждения. Пока файл задачи лежит в git, блокируются `gh pr create/merge`, `glab mr create/merge`, `git merge` в базовую ветку и `git push` в неё; блокируется и `git commit` на базовой ветке с файлом задачи в индексе. Обычный `git push` рабочей ветки (с именем `<type>/<kebab>`, не базовой, в репозитории сессии, на настроенный remote, без добавок из конфига push) проходит без вопроса; любой другой push требует подтверждения, `--force` и `--mirror` заблокированы (условия и остаточный риск: README, раздел guard). Папки задаёт ключ `workDocs` (по умолчанию `["docs/tasks"]`, `[]` выключает правило). **Review gate:** те же команды без вердикта `Yes` ревьюера для приземляемого коммита требуют подтверждения. Запись вердикта guard пишет для каждого элемента `details.results[]` с `agent === "reviewer"` в результате инструмента `subagent`, из его `finalOutput` (`Reviewed BASE:`, `Reviewed HEAD:` и `Ready to merge:`, вместе с отчётом); неудачный запуск ревьюера (ненулевой `exitCode` или нет вывода) считается Inconclusive, как и ревью, прошедшее, пока правки были не проверены (в проекте с командами проверки), а ревью в рамках одного сообщения пользователя (событие `input`) сливаются в худший вердикт. Вызов `bash` с `gh pr create`/`glab mr create` запоминает свою ветку там, где команда начинается (`tool_call`), и регистрирует её, когда его `tool_result` успешен или падает после шага с PR. Отчёт без одной из трёх строк считается Inconclusive. Если проверка падает с ошибкой, pi блокирует вызов. Записи лежат в `<tmpdir>/eng-kit/reviews/<sha1(общей git-директории репозитория)>/`, по файлу на запуск ревьюера и коммит, удаляются через 30 дней, и им доверяют, только если папка принадлежит текущему пользователю. Правка `.pi/guard.json` (edit/write или не read-only shell-команда с этим путём) требует подтверждения; запись в записи вердиктов (edit/write или shell-команда с их путём) блокируется | `allow`, `workDocs` и `reviewGate` работают только в trusted-проекте: чужой репозиторий не должен ослаблять защиту. Review gate спрашивает, а не блокирует, потому что фоновый запуск pi-subagents может не вернуть отчёт в этот результат. Без UI подтверждение невозможно, поэтому такие вызовы блокируются |
| `verify.ts` | Команды из `.pi/verify.json` или из `## Commands` в AGENTS.md. `/verify` и инструмент `run_verification`. После `edit`/`write` рабочая копия считается непроверенной. На `agent_end` агент получает follow-up, **не больше одного на сообщение пользователя**. В том же follow-up ещё два гейта. **Approval gate:** файл задачи со `Status: design approved` или `plan approved` не закоммичен; на базовой ветке он велит сначала создать рабочую ветку. **Working-docs gate:** файл задачи, где в `## Plan` отмечены все чекбоксы, пора закрыть: перенести долгоживущее в `docs/` и `docs/decisions/`, показать его Follow-ups и удалить. Состояние verify, которое читает guard, лежит на `globalThis`: pi загружает каждое расширение в своём графе модулей, и объект на уровне модуля был бы у каждого расширения свой | Доказательством считается только точный прогон команды: без pipe (он прячет код выхода), без `cd`, без фильтра. Одобрение, которого нет в git, можно потерять или тихо изменить; законченный файл задачи в дереве становится устаревшим контекстом |
| `init.ts` | `/kit-init` создаёт недостающие `.pi/verify.json`, `guard.json`, `model-routing.json` и добавляет `pi-subagents` в `settings.json`. Существующие файлы не перезаписывает, кроме старой копии скрипта test-hygiene. Сообщает, если CI запускает не все команды проверки или в нём нет job `working-docs`. Предлагает скрипт `test-hygiene` и копирует его в `.ci/test-hygiene.mts` (ES-модуль, что бы ни говорил `package.json`) только по `/kit-init --test-hygiene`; тот же флаг заменяет копию старше версии пакета (версии сравниваются как числа). Сообщает о старой копии и о CI, который скрипт не запускает, в том же прогоне, что его добавляет. Дополнение предлагает `--yes` и `--test-hygiene` и сохраняет уже набранные флаги | AGENTS.md намеренно не пишется шаблоном: файл, который агент соберёт по коду и проверенным командам, лучше заготовки с плейсхолдерами |
| `models.ts` | `model-routing.json`: режимы (`deep`, `fast`, `cheap`) и привязка команд к режимам. `/review` переключает модель и thinking до начала хода. `/mode` — вручную. Модель может быть списком | Самая сильная модель — для ревью и планов, средняя — для исполнения. Проектный файл действует только в trusted-проекте. Follow-up гейта модель не меняет |

## 5. Промпты и шаблоны

**Два вида документов.**
- **Рабочие** записывают намерение и прогресс: один файл задачи на единицу работы, заполняется по ходу (`brainstorming`, `writing-plans`, `executing-plans`) и живёт только в рабочей ветке. У ограниченной (Bounded) работы его нет, она остаётся в чате.
- **Системные** описывают, что есть сейчас: README, главы `docs/NN-topic.md` с индексом `docs/README.md`, записи решений, CHANGELOG. В базовую ветку попадают только они. Создаёт их `/docs`, а поддерживают в актуальном виде блок Post-implementation и шаг docs при исполнении плана.

| Документ | Где живёт | Статусы | Конец жизни |
|---|---|---|---|
| Файл задачи | `docs/tasks/YYYY-MM-DD-<slug>.md`, только рабочая ветка | `draft → design approved → plan approved → in progress` | удаляется на финише, после того как показаны его Follow-ups |
| Запись решения | `docs/decisions/NNNN-slug.md` | нет: только действующее решение | переписывается на месте, когда решение меняется, и удаляется, когда перестаёт действовать |

**Завершение фичи** (`executing-plans`, Finish, шаг 2): поведение переносится в главу по теме, решения и долгоживущие rulings — в `docs/decisions/`, тебе показываются Follow-ups задачи, после чего файл задачи удаляется одним коммитом `docs: remove the task file for <feature>`. Git его хранит; описание PR ссылается на него на последнем коммите, где он ещё был. Roadmap нет: каждый follow-up становится своим файлом задачи, веткой и PR.

**Записи решений** живые: одна тема на файл, номер — стабильный идентификатор для ссылок («см. решение 0007»), разделы Decision, Why, Consequences, Considered and rejected. Статуса, даты и истории изменений нет. Личные заметки — в памяти агента, а не в репозитории.

- **Промпты** — тонкие входы в скиллы: `/brainstorm`, `/plan`, `/implement`, `/review`, `/debug`, `/onboard`, `/finish`, `/new-task`, `/docs`. Методика живёт только в скиллах.
- **`templates/AGENTS.md`**: структура, команды, раздел Docs, правила, границы «спроси / никогда», DoD. Версии указываются ссылкой на источник, а не числом. В разделе Docs:
  - индекс (`docs/README.md`, `llms.txt`, если он есть в репозитории) и таблица «Задача → С чего начать», чтобы агент читал только то, что нужно задаче;
  - какой источник главнее: код, тесты и CI говорят, что есть; записи решений — какие правила действуют и почему; тематические docs описывают. Противоречие — это баг, о нём сообщают, а не выбирают молча;
  - правило файлов задач.

  pi читает `AGENTS.md` только из рабочей директории и её родителей, поэтому в монорепозитории собственный `AGENTS.md` пакета действует, когда pi запущен в этом пакете; к docs пакетов ведёт карта задач в корне.
- **`templates/task.md`**: файл задачи (раздел 3). `/new-task` пишет только его описание, `/plan <файл задачи>` заполняет Plan, а `/implement <путь>` запускает executing-plans, если Plan заполнен, и короткий путь в остальных случаях.
- **`templates/settings.json`, `guard.json`, `verify.json`, `model-routing.json`** — примеры проектных настроек.

## Ревью и после push

**Ревью** (`requesting-code-review`, агент `reviewer`):
- **фиксированная серьёзность** по таблице в чеклисте. Critical — секреты, инъекции и authZ, потеря денег или данных, тест ослаблен, пропущен или изменён не так, как разрешает «Changing tests» в test-standard, закоммиченный фокусный тест, удалённая, пропущенная или с ретраями проверка CI, ретраи в конфиге раннера, код-заглушка, подавленные ошибки типов или линтера без причины. Important — критерий без теста или с ручной проверкой, которая не нужна или не согласована, строка Review focus плана без теста, тест без assert или с эхом мока, ожидаемое значение, скопированное из вывода кода или пересчитанное его алгоритмом, тестовый хелпер в продовом коде, фиксированный sleep или настоящая сеть вне sandbox-набора, платежи без теста на sandbox провайдера, POS без списка того, что прогнано на реальном железе, устаревшие docs, неотмеченное ломающее изменение, функция длиннее ~100 строк или файл длиннее ~1000 строк;
- **только проверенный код:** ревью, прошедшее, пока правки были не проверены (verify-гейт не зелёный), записывается как Inconclusive; сначала проверки, потом ревью;
- **правила против уговоров:** «так везде в проекте» — это долг, а не разрешение; серьёзность не снижается под давлением аргументов; оцениваются изменённые строки и то, что они ломают;
- **правка правил в самом diff:** если diff меняет правила (манифест агента, конфиг линтера, стандарты), он оценивается по правилам базовой ветки;
- **повторный раунд:** проверяется только новое с прошлого ревью, каждая прежняя находка перепроверяется;
- **правила проекта:** ревьюер читает AGENTS.md и записи решений, которые diff затрагивает или на которые ссылается; нарушение любого из них — Important;
- **правила проекта с цитатой:** находка против правила называет его (файл с заголовком, якорем или ID) и приводит короткую цитату;
- **не дублировать CI:** то, что проверяют команды проверки и линтеры (формат, lint, типы), ревьюер не повторяет — только если проверка падает или отсутствует. Многословный текст — максимум одно сгруппированное Minor;
- **повторный раунд по дефекту:** находки сопоставляются по сути дефекта, а не по формулировке; тот же дефект другими словами — не новая находка;
- **несколько ревьюеров** (платежи, auth, миграции) сливаются по первопричине; на одном `file:line` остаётся более высокая серьёзность, общий вердикт — худший;
- **вердикт** `Ready to merge: <ровно одно из Yes, No, With fixes, Inconclusive>` и строки `Reviewed BASE: <sha>` и `Reviewed HEAD: <sha>`; повторённый шаблон (`Yes / No / …`) вердиктом не считается. Inconclusive — ревьюер не смог прочитать требования, диапазон или правила;
- **без мусора:** никакой похвалы и выдуманных ссылок.

**Review gate** (механика, а не инструкция). Перед `gh pr create`, `glab mr create`, `git merge` в базовую ветку, `git push` в неё и `git push` в ветку PR, который открыл агент (регистрируется после успешного `gh pr create`/`glab mr create` и забывается, когда голова PR `origin/<ветка>` попала в базу, или через 30 дней), guard спрашивает тебя, если последний вердикт ревьюера для этого коммита не `Yes` или его диапазон не доходит до удалённой базы (без UI — блок). Доходит, если `Reviewed BASE` записи лежит в базовой ветке push-remote (иначе `origin`, иначе любого remote; в локальной базе — только когда её не отслеживает ни один remote) или сам является коммитом, ревью которого засчитывается по тому же правилу, не больше 20 раундов и 300 вызовов git. Раунд должен начинаться с самого нового отревьюенного коммита под ним, чтобы не пропускать находки раунда. Повторный раунд смотрит только новые коммиты, а находки прошлого раунда его ревьюер читает через `scripts/review-log.ts`, а не со слов автора. Пустой диапазон, цепочка, разорванная rebase, и запись без диапазона ничего не покрывают. Запись вердикта guard пишет из результата `subagent` с отчётом ревьюера, поэтому ревьюер запускается не в фоне; считаются только запуски `reviewer`, а ревью, прошедшее, пока правки были не проверены, записывается как `Inconclusive`. Вердикт покрывает ровно тот коммит, который ревьюер отревьюил: любое изменение после него (новый коммит, amend, rebase на свежую базу, правка документации, удаление файла задачи) требует нового ревью, и ветка только с документацией ревьюится так же, поэтому финальное ревью идёт последним — после docs, удаления файла задачи и rebase. Коммиты, уже лежащие в удалённой базе, ничего нового не приземляют. Записи хранятся по запуску ревьюера и по коммиту, поэтому ревью другой ветки не забывает эту. `cd <dir>` и `git -C <dir>` отслеживаются, поэтому ветка worktree проверяется там, где выполняется команда. Приземление в цепочке после любого шага, кроме read-only и команд проверки проекта (`git commit … && gh pr create`, `git switch main && git merge …`) требует подтверждения: guard не видит, что оно приземляет. Merge PR/MR (`gh pr merge`, `glab mr merge`) спрашивает всегда, каким бы ни был вердикт; `gh pr create --head <ветка>` проверяет эту ветку. `With fixes`, `No` и `Inconclusive` не пропускают. Отключает гейт только пользователь: подтверждением или `"reviewGate": false` в `.pi/guard.json` (trusted-проект). Самопроверка без `subagent` гейт не проходит, решение остаётся за тобой.

**Ответ на ревью** (`receiving-code-review`): каждое замечание либо исправлено, либо на него дан ответ; ни одно не пропускается молча. Нельзя писать «решено», пока открыт блокер или пока повторное ревью не закрыло находку. Замечание или поправка, которые повторятся, превращаются в предложенную проверку или правило, начиная с самого сильного уровня (механическая проверка, потом правило проекта, потом правка кита через writing-skills); решает пользователь, а нерешённые предложения попадают в Follow-ups задачи.

**Люди в цепочке** (`ci-quality-gates`, только с твоего «да»): одно обязательное одобрение человека (AI-ревью его дополняет, но не заменяет) и CODEOWNERS на файлы, которые управляют остальными: манифест агента и его папка, path-правила, CI, `docs/decisions/`, конфиги линтера и типов.

**После push** (`git-workflow`):
- CI отслеживается инструментом хостинга, а не самописным циклом;
- на каждую упавшую проверку — не больше двух попыток с найденной причиной, дальше вопрос тебе;
- агент никогда не мержит сам;
- rebase своей ветки — только `--force-with-lease=<ветка>:<sha>`.

**Процессы:** dev-серверы и watchers работают в фоне; агент останавливает только то, что запустил сам.

## Два контура проверок: сессия и CI

- **Сессия агента.** TDD, verify-гейт после каждой правки, approval gate и working-docs gate, guard, ревью. Ловит проблему сразу, пока агент работает.
- **CI проекта** (`ci-quality-gates`). Работает на каждом изменении, кто бы его ни сделал, и не зависит от хуков и модели:
  - минимум всё из `verify.json`;
  - один обязательный `gate` (в нём `e2e`, только если такой job есть в проекте);
  - по стеку и только с твоего «да»: гигиена тестов, e2e без ретраев, чьи JUnit-отчёты проверяет `--junit test-results/` (только отчёты), sandbox провайдеров отдельным job, поиск секретов и аудит зависимостей, миграции и дрейф схемы, контракты, покрытие как пол по расписанию;
  - job `working-docs`: падает на любом отслеживаемом `docs/tasks/*.md` в базовой ветке, кто бы его туда ни принёс.
- **Скрипт `test-hygiene`** (`scripts/test-hygiene.ts`): один файл без зависимостей, нужен только Node ≥22.18, какой бы ни был стек проекта. `/kit-init` предлагает его и копирует в `.ci/test-hygiene.mts` (ES-модуль, что бы ни говорил `package.json` проекта) только по `/kit-init --test-hygiene` после твоего «да». Тот же флаг заменяет более старую копию (версии сравниваются как числа), а пробел в CI виден в том же прогоне. Запускают его job `test-hygiene` и `e2e` из шаблонов ci-quality-gates. Он проверяет:
  - фокусные тесты и skip без ссылки на задачу (`#123`, URL или `ABC-123`; причины словами мало, кроме skip по платформе или режиму тестов, чья причина начинается с `platform:` или `mode:`) в JS/TS (Playwright `test.describe.only/skip/fixme`, Cypress, раскладки Mocha и Nest), Python, JVM, Go, Swift, .NET, Gherkin; фиксированные sleep; ретраи в конфигах раннеров и в коде тестов (`this.retries`, `describe.configure`, pytest `flaky`);
  - `--junit <dir>` сам по себе проверяет только отчёты: отсутствующий или пустой, либо заявленное число тестов не совпадает с прогнанными (упавший шард).

  В существующем проекте это храповик: считаются только строки, которые добавляет изменение (переименования отслеживаются), а старый долг показывается в сводке и не блокирует (`--all` проверяет все строки). Без merge base скрипт останавливается с сообщением: CI нужен `fetch-depth: 0`, а в GitLab — явный fetch целевой ветки. `test-hygiene: allow <причина>` помечает строку, где паттерн и есть проверяемое поведение; allow без причины сам считается нарушением, а allow, скрывающий запрещённый skip, ретрай или sleep, — только с твоего согласия. `.ci/test-hygiene.json` добавляет тестовые файлы, исключения и паттерны. Рядом — родные линтеры стека (таблица в `ci-quality-gates/references/ci-templates.md`).
- **Команды проверки в Turbo-монорепе.** Если есть `turbo.json` (или `turbo.jsonc`, комментарии допустимы), `kit-init` определяет одну команду `<exec> turbo run typecheck lint test` из объявленных в нём задач; ключ `pkg#task` объявляет `task`, а `<exec>` — `pnpm`, `yarn`, `bunx --no-install` или `npx --no` по lockfile, так что запускается только локально установленный turbo. Раздел Commands манифеста по-прежнему главнее, а нечитаемый `turbo.json` или без этих задач отдаёт выбор скриптам `package.json`. Один `pnpm-workspace.yaml` выбирает pnpm. Покрытие CI: команда проверки Turbo считается покрытой, если шаг CI запускает `turbo run` со всеми её задачами, в любом порядке и с безвредными флагами (`--affected`, `--continue`, `--cache-dir` и другие флаги вывода и производительности); `--filter`, `-F` и `--dry-run` сужают запуск, поэтому не покрывают. Остальные команды сверяются как текст.
- **Обратимые миграции шаблона.** Каждая миграция шаблона `ts-monorepo` поставляется с `down.sql`. `pnpm --filter @repo/db migrate:down <name>` откатывает последнюю применённую миграцию этим файлом в одной транзакции и помечает строку истории как откатанную; `migrate deploy` применяет её снова. У Prisma нет своих down-миграций, а `migrate resolve --rolled-back` принимает только неудавшиеся, поэтому скрипт сам обновляет строку. Запускай его только после отката кода, которому миграция нужна; он откатывает схему, но не данные, и guard спрашивает перед запуском. `template-smoke` проверяет deploy, откат до пустой схемы и повторный deploy.
- **Job БД в CI шаблона.** В `pr.yml` шаблона есть job `db` в гейте (`needs`): он поднимает Postgres через `pnpm db:up`, выполняет deploy, откатывает последнюю миграцию, проверяет, что схема пуста, снова выполняет deploy и проверяет совпадение с `schema.prisma`. Версии Postgres в workflow нет. Собственный `template-smoke` кита разворачивает шаблон с `--postgres 18`.
- **Связка контуров:**
  - `kit-init` механически сверяет, что CI запускает каждую команду проверки, содержит job `working-docs` и запускает `.ci/test-hygiene.mts`, если он есть в проекте, и сообщает, если копия старше версии пакета;
  - ревью считает Important отсутствие команды в CI, а удалённую, пропущенную или с ретраями проверку — Critical.
- **BDD** — опциональный приёмочный слой (`test-driven-development/references/bdd.md`). Каждый видимый пользователю критерий задачи — ровно один сценарий с тегом критерия. Получается цепочка «критерий → сценарий → CI», а теги проверяет ревью по файлу задачи.

## Тестирование

Основа — железное правило TDD: сначала падающий тест, затем минимальный код, затем прогон всего набора. Все остальные правила тестов живут в одном месте — в стандарте `test-driven-development/references/test-standard.md`; TDD, BDD, writing-plans и чеклист ревью ссылаются на него, а не пересказывают:
- **ожидаемые значения** берутся из критериев задачи, а не из вывода кода. Единственное исключение — характеризационные тесты легаси: `*.char.test.*` (или тег стека), они по замыслу проходят с первого запуска и не считаются покрытием нового поведения. Эталонные данные при портировании — приёмочный тест, который сначала падает, а не характеризационный;
- **сначала красный:** каждый новый тест видят падающим, кроме характеризационного;
- **тест должен окупаться:** нет тестов на константы, конфиг, форму схем, «рендерится», эхо мока; одинаковые случаи объединяются в параметризованный тест; снапшоты маленькие и инлайн;
- **структура и имена:** Arrange–Act–Assert, одно поведение на тест, имя = субъект + обстоятельство + результат; тестовые хелперы живут в тестовом коде (кроме фейка провайдера или override флага, которые выбирает конфигурация, а проверка при старте запрещает в продакшене);
- **моки:** фейкуются только неуправляемые зависимости; своя БД и очереди в интеграционных тестах настоящие. Sandbox провайдеров — отдельный набор и отдельный job CI, единственное место, где тест ходит в сеть;
- **детерминизм и изоляция:** время и случайность под контролем, сети нет, есть прогон не в UTC; ожидание — по условию с одним потолком на проект, никогда не фиксированный sleep; тесты работают в любом порядке и параллельно; отсутствующая тестовая инфраструктура (БД, контейнер, эмулятор) роняет прогон, а не пропускает тест;
- **без ретраев:** тест никогда не перезапускается — ни в конфиге раннера, ни в CI, ни циклом. Ожидание условия (web-first assertions, `expect.poll`, `waitFor`) — не ретрай. Flaky считается исправленным, только когда выполнены пять критериев: найдены падающий прогон и граница, устранена первопричина, повторный прогон зелёный на том же коммите, зелёный в той конфигурации, где падал, весь набор зелёный;
- **критерии и уровни:** с BDD у видимого пользователю критерия ровно один сценарий с его тегом; у любого другого критерия — хотя бы один тест на самом дешёвом уровне, который показывает его так, как видит пользователь или вызывающий код; e2e без BDD — только критичные сценарии, по одному пути на тест;
- **ручная проверка** заменяет тест только там, где автоматизация невозможна (реальное железо, ревью стора, фискальное устройство, физическая подпись): в файле задачи — причина, ты согласен, отчёт говорит, что она выполнена. В остальных случаях критерий без теста — пробел;
- **outside-in с BDD:** сначала пишется сценарий и видно, как он падает, затем unit-циклы TDD ведут код, а прошедший сценарий закрывает критерий. Unit-тесты под ним проверяют собственный контракт своего модуля и остаются; не пишется только unit-тест, который проверяет тот же пользовательский результат, что уже доказывает сценарий;
- **изменение тестов:** удаление теста вместе с его поведением или теста, который ничего не защищал, требует только причины в коммите; правка assert, удаление теста, чьё поведение осталось, skip или карантин — только с твоего согласия и отдельным коммитом; у skip есть ссылка на задачу (кроме skip с причиной `platform:`/`mode:`). `test-hygiene: allow <причина>` — для паттерна, который и есть проверяемое поведение; скрыть им запрещённый skip, ретрай или sleep можно только с твоего согласия, и ревью оценивает это как сам паттерн;
- **покрытие** — пол, а не цель; визуальные эталоны создаются только в CI.

План называет тест для каждого критерия, а описание PR — как каждый новый тест видели красным. Ревьюер проверяет правила с фиксированной серьёзностью из чеклиста. Механический слой (скрипт `test-hygiene` и линтеры стека) ci-quality-gates добавляет только с твоего «да».

## 6. Принципы, заложенные в пакет

1. Три пути процесса вместо одного тяжёлого, чтобы мелкие задачи не тонули в бюрократии.
2. Методика — в скиллах, механика — в расширениях, точки входа — тонкие. Правила готовности живут в одном месте.
3. Никаких узких вендорных скиллов: доменная суть без привязки к конкретному провайдеру или библиотеке. Проектная специфика — в AGENTS.md проекта.
4. Сабагенты — через `pi-subagents`, если он установлен. Иначе работа идёт inline, выдуманных вызовов инструментов нет.
5. Свою рабочую ветку с именем по соглашению агент пушит без вопроса; любой другой push требует подтверждения, а merge, push в базовую ветку и переписывание опубликованной истории остаются за тобой. Проекту с другим соглашением об именах нужно узкое `allow` в `.pi/guard.json`, например `^git push( -u)? origin (story|task)/[a-z0-9._-]+$`. `allow` снимает все вопросы guard для подходящей команды, поэтому держи шаблоны якорными.
6. Скиллы на английском: так точнее срабатывание. Документация — на английском, у каждого файла есть русская версия (`*.ru.md`).
7. У каждого документа хранится только текущая версия: файлы задач удаляются, когда работа сделана, записи решений переписываются на месте. Историю хранит git, поэтому контекст, который читает агент, остаётся небольшим и непротиворечивым.

## 7. Как это проверено

- **`npm test`**:
  - guard (классификатор push своей ветки: тихие формы, каждое подтверждение и блок, проверки конфига, окружения и remote; блок, подтверждение, allow, конфиг, пути, файлы задач в базовой ветке, review gate: запись вердикта только из результатов `reviewer` в `subagent`, неудачный запуск как Inconclusive для своего коммита, слияние вердиктов, параллельные запуски, код после ревью, удалённая база, rebase, worktree и `cd`, приземления в цепочке, merge PR/MR, запись через shell, `reviewGate` только в trusted-проекте, ревью непроверенных правок как Inconclusive, цепочка диапазонов, review-log, push в ветку открытого PR, упавшая проверка guard, проект через symlink);
  - парсер команд и правило доказательства;
  - bootstrap в каждом запросе;
  - verify-гейт (одно напоминание, снятие после зелёного прогона), approval gate и working-docs gate;
  - маршрутизация моделей;
  - `scripts/test-hygiene.ts` (правила на 7 языках, храповик с переименованиями, нет merge base, только JUnit-отчёты, конфиг, CLI);
  - `/kit-init` (в том числе пункт test-hygiene: предложен, копируется с `--test-hygiene`, старая копия видна в отчёте и заменяется по флагу, CI без него виден в том же прогоне; дополнение нескольких флагов; покрытие CI с учётом Turbo: `turbo run` с задачами команды проверки в любом порядке или с безвредными флагами её покрывает, `--filter`, `-F` и `--dry-run` нет, а цепочка или команда проверки с флагами сверяется как текст);
  - состояние verify, общее с guard, у расширений, загруженных в разных графах модулей;
  - манифест пакета и линтер всех скиллов и промптов.
  - шаблон `ts-monorepo` (нет версий, `scaffold.json` называет существующие воркспейсы, действия закреплены по SHA) и скрипт scaffold (отказ для непустой папки, планируемые установки, `.nvmrc`, `packageManager`, `.postgres-version` и разбор аргументов);
- **`npm run typecheck`** против реальных типов pi.
- **`template-smoke`** (`.github/workflows/template-smoke.yml` в собственном CI кита, раз в неделю и на PR, затрагивающих шаблон или скрипт scaffold): разворачивает `ts-monorepo` с `--postgres 18` в чистую папку, поднимает Postgres через `pnpm db:up`, запускает `pnpm turbo run typecheck lint test`, `prisma migrate deploy`, `migrate:down` до пустой схемы и снова `prisma migrate deploy` на Postgres. Он вне `gate` и релиза: красный означает, что экосистема сдвинулась и шаблон надо поправить.
- **Сквозной прогон pi** с локальным mock-LLM на копии `examples/demo`: bootstrap во всех запросах, guard блокирует чтение `.env`, `rm -rf ~/…` и `git push --force`, verify-гейт срабатывает на «Done!», `run_verification` гоняет тесты проекта.

**Не проверено:** у push своей ветки живого прогона пока нет, его живая проверка — первый push ветки, которая его выпускает; guard для `powershell` на Windows (логика та же, но не прогонялась); живой прогон `worker` с его контрактом отчёта (контракт — текст в executing-plans); review gate с настоящим pi-subagents (формат результата проверен только на фейке, фоновые и workflow-запуски запись вердикта не пишут).

**Известные ограничения push своей ветки:** guard команд видит не всё. Он не видит косвенного запуска: shell-строки с обфускацией кавычками (`sh -c 'g""it …'`), однострочники интерпретаторов (`python -c "os.system('git …')"`), оболочки, которых нет в его списке (`fish -c`), подключаемые и обычные файлы-скрипты, подготовительная команда за обёрткой, которой нет в списке guard (`find -exec`, `caffeinate`, `watch`), git под другим именем (symlink или копия бинарника) или по относительному пути (`bin/git`), переменная перед программой, которая сама запускает git (`gh`, `npm install` с git-зависимостями, `make`, скрипты), переменная, уже экспортированная профилем оболочки пользователя, переменные прокси (`HTTPS_PROXY`, `ALL_PROXY`), `GIT_ALLOW_PROTOCOL` и `export EDITOR=…` (так задумано), метод `gh api`, заданный переопределением в заголовке, и запись shell в `.git/config` или `.git/refs`. Любое из этого может настроить remote или сделать push. Как и `curl`, утечку данных guard не предотвращает. Остальное закрывают серверные CI, ревью и защита веток.

**Известные ограничения review gate:** однострочник интерпретатора всё ещё может спрятать путь от проверок shell; гейт защищает от забытого ревью, а не от агента, который намеренно подсовывает ревьюеру вердикт; он видит только PR, открытые этим агентом; диапазону, который назвал ревьюер, гейт доверяет; remote-tracking refs локальны, поэтому `git update-ref` может подделать влитый PR или уже приземлённый коммит; парсер команд не разбирает heredoc и комментарии `#`, поэтому приземление после них может остаться незамеченным; правило «ревьюер только читает» здесь — инструкция, потому что pi не сообщает guard, какой агент выполняет вызов; без определимой базовой ветки (нет `origin/HEAD`, нет `main`/`master`) он ничего не делает.

## 8. Как развивать

- Новый скилл пишется по `writing-skills`: сначала сценарий без скилла (RED), потом минимальный скилл. Затем `npm test` и строка в этом документе. Субагенты пишутся так же, по `writing-skills/references/agents.md`.
- Правило, которое можно проверить механически, живёт в guard, verify или CI, а не в тексте скилла.
- В шаблоне нет версий: они ставятся из реестра при scaffold, а `template-smoke` показывает, когда экосистема сдвинулась.
- Доменные пакеты под конкретную компанию (конкретный эквайер, ОФД) лучше делать отдельным pi-пакетом поверх этого.
