# pi-engineering-kit: как это устроено

pi-engineering-kit — это пакет для кодинг-агента [pi](https://pi.dev), который делает из него дисциплинированного инженера. Пакет подходит для любого проекта и подстраивается под него по трём независимым осям:
- **где работает код:** web, мобильные приложения (Android, iOS), десктоп (Windows, Linux);
- **что он делает:** от развлекательных приложений до кассовых систем и платежей; там, где ошибка стоит дорого (деньги, фискализация, безопасность), есть отдельные скиллы;
- **в каком состоянии код:** новый проект или существующий, в том числе написанный задолго до агентной разработки.

Поверх этих осей работает один и тот же процесс: дизайн → план → TDD → проверка → ревью → git.

Здесь описано, как устроен пакет и почему он устроен именно так. Как установить и попробовать — в [GETTING-STARTED.ru.md](GETTING-STARTED.ru.md).

---

## 1. Идея в трёх предложениях

1. **Процесс масштабируется по размеру задачи.** Мелкая правка проходит короткий путь, архитектурная — полный путь от спецификации до ревью. При сомнении выбирается более тяжёлый путь.
2. **Модель сама не решает, что работа готова.** Это решают проверки проекта. Гейт в расширении возвращает агента к работе, если после правок не было зелёного прогона.
3. **Необратимое и внешнее проходит через человека.** Расширение guard блокирует опасные команды и спрашивает подтверждение на push, деплой, миграции и публикацию.

## 2. Архитектура

```
┌─────────────────────────────── проект ────────────────────────────────┐
│ AGENTS.md (команды, правила, границы, DoD)   .pi/verify.json   .pi/guard.json │
└──────────────────────────────────┬────────────────────────────────────┘
                                   │ читают
┌──────────────── pi-engineering-kit (этот пакет) ────────────────────────┐
│ extensions/bootstrap.ts  → в каждый запрос: скилл using-skills          │
│ extensions/guard.ts      → tool_call: block / confirm / allow           │
│ extensions/verify.ts     → /verify, run_verification, гейт на agent_end │
│ extensions/models.ts     → модель и thinking по команде, /mode          │
│ extensions/init.ts       → /kit-init: .pi/ проекта одной командой       │
│ skills/   27 скиллов (процесс, старт, платформы, домены), по описанию│
│ prompts/  8 точек входа: /brainstorm /plan /implement /review …         │
│ templates/ AGENTS.md, task.md, settings.json, guard.json, verify.json   │
└─────────────────────────────────────────────────────────────────────────┘
```

**Рабочий цикл:**

```
идея ──/brainstorm──▶ классификация: Spike | Bounded | Architectural
  Spike ─────────▶ проба → рекомендация (код одноразовый)
  Bounded ───────▶ дизайн в чате → «да» → /implement (TDD) → verify → отчёт
  Architectural ─▶ spec → «да» → /plan → «да» → /implement (executing-plans)
                    → requesting-code-review → /finish (merge / PR / keep / discard)
баг ──/debug──▶ systematic-debugging: корень → падающий тест → один фикс → verify
чужой репо ──/onboard──▶ карта → доказанные команды → AGENTS.md + .pi/verify.json
```

**Кто за что отвечает:**
- **Промпты** — тонкие точки входа.
- **Скиллы** содержат всю методику.
- **Расширения** механически обеспечивают то, что нельзя доверить одному тексту.

Благодаря такому разделению пакет не дублирует сам себя: правила готовности живут в одном месте, а не повторяются в каждом промпте.

## 3. Скиллы

### Ядро процесса

| Скилл | Что делает | Почему так |
|---|---|---|
| `using-skills` | Правило «сначала проверь скиллы», приоритеты, три пути (Spike / Bounded / Architectural), таблица «с чего начать», блок «Always true», red flags | Внедряется в каждый запрос, поэтому на нём держатся общие правила: доказательства прежде утверждений, скоуп, тесты, вопросы на развилках, секреты |
| `brainstorming` | Дизайн до кода: классификация работы, по одному вопросу за раз, 2–3 подхода, spec, self-review | Доменные вопросы (деньги, POS, ОС) задаются заранее, потому что потом менять дорого |
| `writing-plans` | План как набор решений, которые исполнитель не примет сам: файлы, сигнатуры, Interfaces, Review focus | План длиннее кода означает, что код уже написан в плане. Исполнение — inline или субагент на задачу |
| `executing-plans` | Исполнение плана с ledger-файлом, «rulings, not stalls», контракт завершения задачи, режим «субагент на задачу» | Ledger — обычный markdown: переживает компакцию и не требует скриптов |
| `test-driven-development` | Iron Law, RED→GREEN→REFACTOR | «Тест, который не был красным, ничего не доказывает» и «не ослабляй тесты ради зелени». Для legacy сначала характеризационные тесты |
| `systematic-debugging` | 4 фазы, трассировка корня, «3 неудачных фикса — вопрос к архитектуре» | Границы систем с примерами для POS и мобильных, правило о flaky-тестах |
| `verification-before-completion` | Гейт IDENTIFY→RUN→READ→VERIFY→CLAIM и формат честного отчёта | Раздельно local / commit / push / CI / deploy / live. Pipe в `tail` прячет код выхода |
| `requesting-code-review` | Ревью в свежем контексте по диапазону SHA, шаблон промпта ревьюера, чеклист | **Подтверждено / Предположения / Вопросы**, в каждой находке триггер, последствие и доказательство. Падение сверяется с базовой ревизией. AI-ревью не заменяет одобрение человека |
| `receiving-code-review` | Проверять перед тем, как внедрять; YAGNI через grep | Отклонение замечания — только с конкретным обоснованием |
| `git-workflow` | Изоляция, baseline, коммиты, 4 варианта завершения ветки | Никогда `--no-verify`, force только `--force-with-lease`, discard только по явному вводу |
| `dispatching-parallel-agents` | Группировка по независимым доменам, самодостаточные промпты | Писатели с непересекающимися файлами, без сабагентов — последовательно |
| `writing-documentation` | Где что лежит (README, docs/, ADR, CHANGELOG, манифест агента, API-справка, комментарии), правила текста и комментариев, что устаревает при изменении кода | Документация — часть изменения: в том же коммите и о текущем состоянии. Перед «docs updated» команды прогнаны, ссылки проверены. Если в проекте свой формат, используется он. Держится на четырёх слоях: правило в этом скилле; блок «Post-implementation» в каждом плане и шаг обновления docs в `/implement` и `executing-plans`; устаревшие docs на ревью — Important; механические проверки (`references/checks.md`) предлагаются в verify и CI проекта |
| `ci-quality-gates` | Проверки в CI проекта | CI запускает минимум всё из verify.json; один обязательный job `gate`; слои по стеку добавляются только с «да»: гигиена тестов, e2e без ретраев с подсчётом прогнанных тестов, секреты и аудит зависимостей, миграции и дрейф, контракты, покрытие как пол по расписанию; защита ветки — только с «да» |
| `updating-dependencies` | Обновление, добавление и удаление зависимостей, SDK и тулчейнов | По одной за раз; changelog прочитан, ломающие изменения выписаны; мажорная версия или новая зависимость — только с «да»; сначала уязвимости; lockfile меняет только пакетный менеджер; полный прогон проверок |
| `writing-skills` | Как писать и тестировать скиллы | Description — только триггеры. Скилл проверяется сценарием без него (RED) |

### Старт: новый или существующий код

| Скилл | Зачем |
|---|---|
| `choosing-a-stack` | Стек выбирается по надёжности для домена. Таблица дефолтов по платформам. **Выбор стека — всегда развилка для пользователя.** Версии сверяются по официальным источникам, а не по памяти |
| `onboarding-existing-codebase` | CI — это правда, команды доказываются прогоном. На выходе AGENTS.md по шаблону и `.pi/verify.json` |
| `changing-legacy-code` | Characterization tests, seams, sprout/wrap, strangler fig. Удаляй только свои сироты: странная ветка может быть требованием |

### Платформы

| Скилл | Зачем |
|---|---|
| `web-frontend` | Семантика и минимум a11y, состояния loading / empty / error / success, гонки и устаревшие ответы, производительность, безопасность, пункты для ревью |
| `backend-services` | Конфиг в одном модуле с проверкой при старте, один артефакт на все окружения, процессы без состояния, readiness и liveness, graceful shutdown по SIGTERM, dev ≈ prod, разовые задачи из релиза, API-контракт как источник правды (12-factor без дублирования observability и database-changes) |
| `mobile-development` | Жизненный цикл, разрешения, безопасность, лестница проверки (unit → release-сборка → эмулятор → устройство). Android и iOS — в `references/` |
| `desktop-development` | UI-поток, пути по платформе, IPC, подпись, автообновление, установка в чистую VM. Windows и Linux — в `references/` |

### Домены с высокой ценой ошибки

| Скилл | Зачем |
|---|---|
| `payments-and-money` | Minor units или decimal, ISO 4217, идемпотентность, state machine, таймаут означает «неизвестно», webhooks, outbox, double-entry, сверка, PCI DSS scope |
| `pos-systems` | Offline-first, очередь синхронизации, неизменяемые чеки, фискализация (54-ФЗ; для других стран — «спроси юрисдикцию»), смены X/Z, периферия за интерфейсами |
| `observability` | Логи (уровни, статичные сообщения, поля, без PII даже в маске), корреляция request/trace id, метрики (RED/USE, ограниченные метки, гистограммы), дедлайны на каждое ожидание, алерты с runbook и на потерю телеметрии, расследование по логам ограниченными запросами |
| `database-changes` | Миграции через expand/contract (работают со старым и новым кодом), обратимость, блокировки, бэкфилл отдельной задачей, порядок деплоя и проверка дрейфа, транзакции и outbox, защитные меры для запросов, жизненный цикл данных, миграции БД на устройствах |
| `security-review` | STRIDE по потокам данных, чеклист (injection, authN/Z, секреты, крипто, supply chain, prompt injection), инструменты, формат находок |

---

**Спека** пишется по шаблону `templates/spec.md`:
- разделы Intent / Context / Success criteria / Scope / Decisions / Design / Rollout / Risks;
- у каждого точный заголовок и один вопрос, пустой раздел помечается «None».

До вопросов агент собирает **карту контекста** (`brainstorming/references/context-map.md`) и пишет намерение, допущения и открытые вопросы. У плана есть `Base:` с SHA коммита, при исполнении проверяется, не ушёл ли код. У PR есть формат описания, и одна тема на PR.

## 4. Расширения

| Расширение | Как устроено | Почему так |
|---|---|---|
| `bootstrap.ts` | На событии `context` вставляет `using-skills` как **user**-сообщение после compactionSummary, с дедупликацией по маркеру | Без bootstrap скиллы инертны: модель видит только их описания. Изменения в `context` не сохраняются в истории, поэтому правила внедряются в **каждый** запрос. Сообщение стоит на стабильной позиции с тем же timestamp и попадает в prompt cache |
| `guard.ts` | Токенизатор с учётом кавычек и цепочек (`&&`, `\|`, `;`). Три решения: block, confirm или allow. Проектный `.pi/guard.json` | `allow` работает только в trusted-проекте: чужой репозиторий не должен ослаблять защиту. Без UI подтверждение невозможно, поэтому такие вызовы блокируются |
| `verify.ts` | Команды из `.pi/verify.json` или из `## Commands` в AGENTS.md. `/verify` и инструмент `run_verification`. После `edit`/`write` рабочая копия считается непроверенной. На `agent_end` агент получает follow-up, **не больше одного на сообщение пользователя** | Доказательством считается только точный прогон команды: без pipe (он прячет код выхода), без `cd`, без фильтра |
| `init.ts` | `/kit-init` создаёт недостающие `.pi/verify.json`, `guard.json`, `model-routing.json` и добавляет `pi-subagents` в `settings.json`. Существующие файлы не перезаписывает | AGENTS.md намеренно не пишется шаблоном: файл, который агент соберёт по коду и проверенным командам, лучше заготовки с плейсхолдерами |
| `models.ts` | `model-routing.json`: режимы (`deep`, `fast`, `cheap`) и привязка команд к режимам. `/review` переключает модель и thinking до начала хода. `/mode` — вручную. Модель может быть списком | Самая сильная модель — для ревью и планов, средняя — для исполнения. Проектный файл действует только в trusted-проекте. Follow-up гейта модель не меняет |

## 5. Промпты и шаблоны

**Два вида документов.**
- **Рабочие** — spec, план, журнал, roadmap, карта легаси. Создаются по ходу работы (`brainstorming`, `writing-plans`, `executing-plans`), записывают намерение и прогресс.
- **Системные** — README, главы `docs/NN-topic.md` с индексом `docs/README.md`, ADR, CHANGELOG. Описывают, что есть сейчас. Создаёт их `/docs`, а поддерживают в актуальном виде блок Post-implementation и шаг docs при исполнении плана.

Когда spec реализована, её долгоживущая часть переходит в главу про эту фичу, а сама spec получает ссылку на главу.

- **Промпты** — тонкие входы в скиллы: `/brainstorm`, `/plan`, `/implement`, `/review`, `/debug`, `/onboard`, `/finish`, `/new-task`, `/docs`. Методика живёт только в скиллах.
- **`templates/AGENTS.md`**: структура, команды, правила, границы «спроси / никогда», DoD. Версии указываются ссылкой на источник, а не числом.
- **`templates/task.md`**: нумерованные проверяемые критерии, ограничения, Out of scope.
- **`templates/settings.json`, `guard.json`, `verify.json`, `model-routing.json`** — примеры проектных настроек.

## Ревью и после push

**Ревью** (`requesting-code-review`, агент `reviewer`):
- **фиксированная серьёзность** по таблице в чеклисте. Critical — секреты, инъекции и authZ, потеря денег или данных, ослабленные тесты, код-заглушка, подавленные ошибки типов или линтера без причины. Important — критерий без теста, устаревшие docs, неотмеченное ломающее изменение, функция длиннее ~100 строк или файл длиннее ~1000 строк;
- **правила против уговоров:** «так везде в проекте» — это долг, а не разрешение; серьёзность не снижается под давлением аргументов; оцениваются изменённые строки и то, что они ломают;
- **правка правил в самом diff:** если diff меняет правила (манифест агента, конфиг линтера, стандарты), он оценивается по правилам базовой ветки;
- **повторный раунд:** проверяется только новое с прошлого ревью, каждая прежняя находка перепроверяется;
- **без мусора:** никакой похвалы и выдуманных ссылок.

**Ответ на ревью** (`receiving-code-review`): каждое замечание либо исправлено, либо на него дан ответ; ни одно не пропускается молча. Нельзя писать «решено», пока открыт блокер.

**После push** (`git-workflow`):
- CI отслеживается инструментом хостинга, а не самописным циклом;
- на каждую упавшую проверку — не больше двух попыток с найденной причиной, дальше вопрос тебе;
- агент никогда не мержит сам;
- rebase своей ветки — только `--force-with-lease=<ветка>:<sha>`.

**Процессы:** dev-серверы и watchers работают в фоне; агент останавливает только то, что запустил сам.

## Два контура проверок: сессия и CI

- **Сессия агента.** TDD, verify-гейт после каждой правки, approval gate, guard, ревью. Ловит проблему сразу, пока агент работает.
- **CI проекта** (`ci-quality-gates`). Работает на каждом изменении, кто бы его ни сделал, и не зависит от хуков и модели:
  - минимум всё из `verify.json`;
  - один обязательный `gate`;
  - по стеку и только с твоего «да»: гигиена тестов, e2e без ретраев с подсчётом прогнанных тестов, поиск секретов и аудит зависимостей, миграции и дрейф схемы, контракты, покрытие как пол по расписанию.
- **Связка контуров:**
  - `kit-init` механически сверяет, что CI запускает каждую команду проверки;
  - ревью считает Important отсутствие команды в CI и ослабленную проверку.
- **BDD** — опциональный приёмочный слой (`test-driven-development/references/bdd.md`). Каждый видимый пользователю критерий spec — один сценарий с тегом критерия. Получается цепочка «критерий → сценарий → CI».

## Тестирование

Основа — железное правило TDD: сначала падающий тест, затем минимальный код, затем прогон всего набора. Всё остальное собрано в стандарте `test-driven-development/references/test-standard.md`:
- **ожидаемые значения** берутся из spec или критерия, а не из вывода кода; характеризационные тесты помечены отдельно;
- **тест должен окупаться:** нет тестов на константы, конфиг, форму схем, «рендерится», эхо мока; одинаковые случаи объединяются в параметризованный тест;
- **структура и имена:** Arrange–Act–Assert, одно поведение на тест, имя = субъект + обстоятельство + результат;
- **моки:** фейкуются только неуправляемые зависимости; своя БД и очереди в интеграционных тестах настоящие;
- **детерминизм и flaky:** время и случайность под контролем, сети нет, есть прогон не в UTC; ретрай не считается исправлением;
- **приёмочный уровень:** каждый критерий задачи → тест, показывающий его так, как видит пользователь (API, UI/e2e, BDD, если он есть в проекте);
- **покрытие** — пол, а не цель.

План называет приёмочный тест для каждого критерия. Ревьюер проверяет эти правила по чеклисту. Механические lint-правила для тестов стандарт предлагает проекту, но не навязывает.

## 6. Принципы, заложенные в пакет

1. Три пути процесса вместо одного тяжёлого, чтобы мелкие задачи не тонули в бюрократии.
2. Методика — в скиллах, механика — в расширениях, точки входа — тонкие. Правила готовности живут в одном месте.
3. Никаких узких вендорных скиллов: доменная суть без привязки к конкретному провайдеру или библиотеке. Проектная специфика — в AGENTS.md проекта.
4. Сабагенты — через `pi-subagents`, если он установлен. Иначе работа идёт inline, выдуманных вызовов инструментов нет.
5. Подтверждение на любой `git push`. Для своих веток его снимает узкое `allow` в `.pi/guard.json`, например `^git push origin feat/`.
6. Скиллы на английском: так точнее срабатывание. Документация — на русском.

## 7. Как это проверено

- **`npm test`**:
  - guard (блок, подтверждение, allow, конфиг, пути);
  - парсер команд и правило доказательства;
  - bootstrap в каждом запросе;
  - verify-гейт (одно напоминание, снятие после зелёного прогона);
  - маршрутизация моделей;
  - `/kit-init`;
  - манифест пакета и линтер всех скиллов и промптов.
- **`npm run typecheck`** против реальных типов pi.
- **Сквозной прогон pi** с локальным mock-LLM на копии `examples/demo`: bootstrap во всех запросах, guard блокирует чтение `.env`, `rm -rf ~/…` и `git push --force`, verify-гейт срабатывает на «Done!», `run_verification` гоняет тесты проекта.

**Не проверено:** guard для `powershell` на Windows (логика та же, но не прогонялась).

## 8. Как развивать

- Новый скилл пишется по `writing-skills`: сначала сценарий без скилла (RED), потом минимальный скилл. Затем `npm test` и строка в этом документе.
- Правило, которое можно проверить механически, живёт в guard, verify или CI, а не в тексте скилла.
- Доменные пакеты под конкретную компанию (конкретный эквайер, ОФД) лучше делать отдельным pi-пакетом поверх этого.
