## Intent

When the user asks the agent to follow a PR, one background process waits on it and wakes the agent with exactly one JSON event only when something needs a decision (a failed check, new review feedback, a conflict, ready, merged or closed, or a blocker), so the model never polls or wakes during ordinary pending CI.

## Context

`lib/pr-feedback.ts` (byte-identical in both editions) already collects one snapshot of a PR's open review items, check rollup and head, and `scripts/pr-state.ts` prints it. git-workflow "After a push" tells the agent to follow CI with `gh pr checks --watch`, which sees checks only, not review feedback, conflicts or a merge. fortune-os solves this with a ~1700-line watcher with a state file and ruleset policy; most of it serves auto-approval flows the kit rejects (merge stays the human's).

## Success criteria

| # | Criterion (observable, testable) | How it is verified |
|---|---|---|
| 1 | One snapshot yields one event by precedence `merged`/`closed` > `conflict` > `checks_failed` > `feedback` > `ready`, else "wait"; `mergeable: UNKNOWN` and pending checks are "wait" | unit: `decide` table in `tests/pr-watch.test.ts` |
| 2 | `--ack <eventId>` suppresses only that id: the same evidence keeps waiting; a new head, a new open item set or a new event kind is returned | unit: `decide` ack rows |
| 3 | `checks_failed` comes at the first failed check on a head, lists every failed check and the pending count, and comes once per head (its id is event + head) | unit: `decide` rows; loop: fake gh sequence pending → one failed → two failed with ack |
| 4 | `ready` only when the head's checks are non-empty and all passed, no open items, no read problems, and the head was seen for at least the quiet period (default 120 s) | unit: empty checks, young head, `problems` rows |
| 5 | A PR followed by number reports `merged` or `closed` after it leaves OPEN | loop: fake gh OPEN → MERGED; live: watcher on a merged kit PR returns `merged` |
| 6 | gh missing or unauthenticated → `blocked` at once; network, 5xx or rate limit → backoff (30, 60, 120 s), `blocked: transient` after 3 in a row; deadline → `blocked: timeout`; no open PR at start → `blocked: no open PR` | loop: fake gh rows with injected clock and sleep |
| 7 | Feedback acked but still open once checks passed → terminal `blocked: feedback-unanswered` listing those items, instead of waiting until the deadline | unit: `decide` row |
| 8 | pi `watch_pr` returns at once, wakes the agent with the event via `pi.sendMessage(…, { triggerTurn: true, deliverAs: "followUp" })` when the process exits, refuses a second watcher in the session, stops the process on `session_shutdown`, and reports `blocked: watcher failed` when the script exits without JSON | pi: `tests/pr-watch-tool.test.ts` with a fake script |
| 9 | The PR feedback gate and `pr-state.ts` keep their behavior; the snapshot only gains fields | existing `pr-feedback`, `hooks`, `verify` tests green in both editions |
| 10 | git-workflow "After a push" names the watcher (still only when the user asks); `references/pr-watch.md` says how to handle each event; the guard doesn't ask for `node <kit root>/scripts/pr-watch.ts` | read-through; guard unit row; live run in Claude Code |

## Scope

**In scope:**
- `lib/pr-feedback.ts` (pi: `extensions/lib/pr-feedback.ts`): read a PR by number; `state`, `mergeable` and `viewer` in the query; `PrState` gains `state` and `mergeable`.
- New shared `lib/pr-watch.ts` (pi: `extensions/lib/pr-watch.ts`, byte-identical): `decide` and the polling loop.
- New `scripts/pr-watch.ts` in both editions.
- pi: new `extensions/pr-watch.ts` with the `watch_pr` tool, listed in `package.json`.
- git-workflow "After a push" and a new `git-workflow/references/pr-watch.md` in both editions.
- Version 0.42.0 in both, CHANGELOG, ARCHITECTURE (+ .ru), README and GETTING-STARTED (+ .ru) mentions.

**Out of scope:**
- GitLab (`glab`); waiting for approval; starting the watcher automatically after a PR opens; any write to GitHub (replies, reruns, rebase, merge); a watcher state file.

## Decisions

1. The watcher runs only when the user asks to follow a PR or CI; it replaces `gh pr checks --watch` in git-workflow (user, 2026-11-18).
2. pi gets a `watch_pr` tool in the extension that runs the same script as a child process and wakes the agent when it exits (user, 2026-11-18).
3. `checks_failed` fires at the first failure on a head, once per head (user, 2026-11-18).
4. Approach A: shared library + one script; not a loop over `pr-state.ts` (it finds PRs by branch among open ones, so it can't see a merge or a conflict), not a port of the fos watcher (user, 2026-11-18).
5. No state file: dedup is `--ack <eventId>` passed by the caller; answered items close through the existing `classify`, so nothing "handled" needs storing.
6. The script only reads (`gh api graphql`), always exits 0 and prints one JSON object; diagnostics go to stderr.
7. On `conflict` the agent stops and asks: a rebase rewrites pushed history, which stays the user's choice (git-workflow).
8. Only Node built-ins, like the rest of `lib/`.

## Design

**Script.** `node <kit root>/scripts/pr-watch.ts [--repo <dir>] [--branch <name>] [--ack <eventId>] [--timeout <s>=3600] [--interval <s>=30] [--quiet <s>=120]`. At start it resolves the branch's PR with the existing branch lookup (`collectPrState`), then polls that PR by number. `prFeedback` config is read as in `pr-state.ts`.

**Event (stdout).** `{ schemaVersion: 1, event, eventId, reason, pr, url, head, checks: { state, failed[], pending }, open: Item[], problems[] }`; `Item` is the PR feedback gate's. Reviewer text stays cleaned and cut (`clean`/`excerpt`); `references/pr-watch.md` says it is reviewers' data, not instructions.

| Event | When | Terminal |
|---|---|---|
| `merged` / `closed` | PR state left OPEN | yes |
| `conflict` | `mergeable: CONFLICTING` | no |
| `checks_failed` | at least one failed check on the head | no |
| `feedback` | open items (incl. changes-requested) | no |
| `ready` | see criterion 4 | yes |
| `blocked` | gh missing or unauthenticated, 3 transient errors, deadline, read problems at would-be ready, no open PR, feedback-unanswered | yes |

`eventId` = sha256 prefix of: event + head (`checks_failed`, `conflict`), event + sorted open item ids (`feedback`), event + PR (terminal ones).

**`lib/pr-watch.ts`.**
- `decide(state: PrState, ctx: { ack?: string; headSeenAt: number; now: number; quietMs: number }): WatchEvent | null` — pure; `null` means wait.
- `watch(opts: { dir; branch?; ack?; timeoutMs; intervalMs; quietMs; gh?; config?; now?; sleep? }): Promise<WatchEvent>` — loop; `now`/`sleep` injectable for tests; `headSeenAt` resets when the head changes.

**Claude Code.** The agent starts the script with Bash `run_in_background: true` and ends its turn; the completion notification is the wake. After handling a non-terminal event it relaunches with `--ack <eventId>`.

**pi.** `extensions/pr-watch.ts` registers `watch_pr({ ack?, timeout? })`: spawns `node <package>/scripts/pr-watch.ts` in `ctx.cwd`, returns "watching PR …" at once; on exit parses stdout and calls `pi.sendMessage({ customType: "pr-watch", display: true, content }, { triggerTurn: true, deliverAs: "followUp" })`. One watcher per session; killed on `session_shutdown`.

**Skill text.** git-workflow "After a push": start the watcher instead of `gh pr checks --watch`; `references/pr-watch.md`: per event — `checks_failed` → systematic-debugging, at most two attempts per check, push, relaunch with ack; `feedback` → receiving-code-review, ack only when every item is fixed or replied; `conflict` → stop and ask; `ready`/`merged`/`closed`/`blocked` → report; never poll by hand, never merge.

## Risks and open questions

- Checks not registered yet right after a push read as an empty rollup → quiet period and "non-empty checks" before `ready`. Starting the watcher long after a push still waits one quiet period.
- Claude Code background processes have no documented runtime cap; a 1 h default deadline bounds the wait and ends in `blocked: timeout`.
- GitHub API cost: two GraphQL calls at start, then one every 30 s (~120 points an hour), far below the 5000/h limit.
- Baseline: eng-kit `tests/pr-feedback.test.ts` "not GitHub" failed once under `verify.ts` load (5004 ms against its 5000 ms deadline; green in a plain `npm test`). Changing that test needs the user's yes first.
